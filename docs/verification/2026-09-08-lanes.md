# Verification: the explore/exploit lanes

Date: 2026-09-08. Copilot CLI 1.0.83. Everything below was produced by running
the thing, not by reading about it.

## 1. The containment hook actually denies

The one claim the whole structure rests on: that a `preToolUse` hook returning a
deny payload really stops a write. The payload schema
(`{"permissionDecision": "deny", "permissionDecisionReason": "…"}`) came from a
web search, and on this platform's track record that is not good enough.

Setup: a scaffolded project, the plugin loaded live, and permissions turned
*all the way off* so that nothing but the hook could refuse:

```bash
cd /tmp/lanecheck && uv run --project ~/MLRAgents mlragents init --name lanecheck
MLRAGENTS_ROLE=explore copilot --plugin-dir ~/MLRAgents --allow-all-tools \
  -p "Create a file at exploit/notes.md containing the single word hello."
```

Result — the write was refused, and the model was told exactly why:

```
✗ Create notes.md
  │ exploit/notes.md
  └ Denied by preToolUse hook: /tmp/lanecheck/exploit/notes.md is outside the
    explore lane (explore/). Exploratory work stays in its own tree so that
    nothing it produces can be cited. To promote a finding, re-run the
    experiment in the exploit lane rather than writing there from an explore
    session.
```

The model then verified `exploit/` was untouched and reported "I did not attempt
to bypass the hook." Two things are confirmed: the schema is right, and it
overrides `--allow-all-tools` rather than being a permission the user can
pre-grant away.

The complementary case, so the guardrail is not simply refusing everything:

```bash
MLRAGENTS_ROLE=explore copilot --plugin-dir ~/MLRAgents --allow-all-tools \
  -p "Create a file at explore/notes.md containing the single word hello."
```

Created, no prompt, `explore/notes.md` contains `hello`.

## 4. Phase 2: the four agents and seven skills load

Run in a scaffolded project with the plugin loaded live, permissions off:

```bash
MLRAGENTS_ROLE=paper copilot --plugin-dir ~/MLRAgents --allow-all-tools \
  -p "List every skill available to you, and every agent you can delegate to.
      Then create paper/plot.py containing 'x=1'."
```

The session listed all seven skills under the MLRAgents plugin
(`debugging-a-failed-job`, `designing-an-ablation`,
`initializing-a-research-repo`, `keeping-the-paper-reproducible`,
`promoting-an-experiment`, `reading-run-results`, `writing-results-prose`) and
all four custom agents (`mlragents:analysis`, `mlragents:experiment`,
`mlragents:explore`, `mlragents:paper`). Skills are discovered from `skills/*/SKILL.md`
by convention; no manifest key is needed.

The write was refused:

```
✗ Create plot.py
  │ paper/plot.py
  └ Denied by preToolUse hook: /tmp/p2check/paper/plot.py is not a .tex or .bib
    file under paper/. The paper role writes prose and references, nothing else.
```

The same file, from the `analysis` role, was created without a prompt. The
confinement therefore discriminates by role rather than by path alone.

## 5. Phase 3: the four guardrails fire on real input

Each guardrail was driven through the real hook shim (`hooks/mlragents-hook`),
not through the Python API, so the JSON contract and the `uv` invocation are
covered too.

**Submission gate.** With an uncommitted change in the worktree, an `sbatch`
call was denied, and the reason named the escape hatch:

```
Denied by preToolUse hook: refusing to submit a job from a dirty worktree.
Uncommitted: src/model.py. A run whose code is not committed cannot be cited.
Commit, or set MLRAGENTS_ALLOW_DIRTY=1 to override.
```

In a real session the model reported the denial and did not set the override on
its own initiative — which is the behaviour the escape hatch depends on.

**Generated-config gate.** Editing a file under a `paths.generated` directory
was denied with a reason naming `commands.generate`. A `.mlragents.toml` edit
outside those directories returned `{}`.

**Provenance recording.** After a successful `sbatch`, `postToolUse` wrote
`job/555001 exploit 555001 … submitted` to the registry. Provenance is captured
at submit time because it records the commit, which `sacct` does not know and
no later scan can recover.

**Numeric audit.** `agentStop` returned `decision: block` on a `.tex` change
carrying an unsourced number, and correctly ignored `\documentclass[11pt]`,
`%`-comments, and macro-only lines.

### A cwd bug the guardrails exposed

`hooks/mlragents-hook` used `uv run --directory <plugin>`, which *changes the
working directory*. A hook payload that omits `cwd` therefore resolved against
the plugin's own `.mlragents.toml` rather than the user's project. Fixed to
`uv run --quiet --project <plugin>`, which sets the project without moving cwd.
`tests/test_hooks.py` now carries the regression.

## 6. Installing from a private repository, and the `/remote` conflict

`/remote` appeared to conflict with the plugin. It does not. `/remote` binds the
session to the detected GitHub repository, and this repository had never been
pushed, so the API answered `409 Git Repository is empty`. In a scratch
directory with no GitHub remote, the same session fell back to the working
repo-less form `https://github.com/copilot/tasks/<uuid>`. Pushing `main` fixed
it; the log now shows `Remote session access enabled` with no 409, and the task
URL resolves against `kailen-hargenrader/MLRAgents`.

Installing then hit a second, unrelated problem. `copilot plugin marketplace add
kailen-hargenrader/MLRAgents` runs an *anonymous* HTTPS clone and cannot read a
private repository. The `ssh://` form works and needs no change to git config
and no publishing:

```bash
copilot plugin marketplace add ssh://git@github.com/kailen-hargenrader/MLRAgents.git
copilot plugin install mlragents@mlragents      # Installed 7 skills, 401K
```

From that installed copy: `/remote` connects, the session reports
`Loading: 2 plugins, 5 hooks`, and `--agent=mlragents:experiment` reaches the
bundled MCP server — `jobs_queue` returned live Slurm rows.

One grammar note. The `--allow-tool` *flag* takes the server name:

```bash
copilot --allow-tool mlragents        # works
copilot --allow-tool mlragents-jobs_queue   # "Permission denied"
```

This is a different mechanism from an agent's `tools:` frontmatter allowlist,
which still requires each MCP tool spelled out in full (§ platform facts).
