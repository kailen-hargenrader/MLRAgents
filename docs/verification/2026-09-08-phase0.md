`/resnick/home/khargenr/MLRAgents` at commit `ed18d04`.

## 2. The plugin installs

```
$ copilot plugin install ./
Plugin "mlragents" installed successfully.

Warning: Direct plugin installs (repos, URLs, local paths) are deprecated. Only
plugin@marketplace installs will be supported in a future release.

$ copilot plugin list
  • superpowers@superpowers-marketplace (v6.3.0)
  • mlragents (v0.1.0)
```

**Held, with a warning that changes the distribution plan.** Direct installs
from a repo, URL or local path are deprecated; only `plugin@marketplace`
installs will survive. Shipping `.claude-plugin/marketplace.json` was already
planned and is now mandatory, and the documented install path must be:

```
copilot plugin marketplace add kailen-hargenrader/MLRAgents
copilot plugin install mlragents@mlragents
```

## 3. Plugin-contributed agents are namespaced

```
$ copilot -p "Reply with exactly: AGENT OK" --agent=experiment --allow-tool='read' -s
No such agent: experiment, available: mlragents:experiment

$ copilot -p "Reply with exactly: AGENT OK" --agent=mlragents:experiment --allow-tool='read' -s
AGENT OK
```

**Did not hold as documented.** The docs state an agent's id is its filename
minus `.agent.md`. For agents contributed by a plugin the id is
`<plugin-name>:<filename>`. A bare id fails outright.

**Consequence.** Every documented invocation, launcher script and skill that
names an agent must use the `mlragents:` prefix. Spec §2 amended.

## 5. A local-path install is a full copy, not a live link

```
$ find ~/.copilot/installed-plugins/_direct/MLRAgents -maxdepth 2
... .venv/ .pytest_cache/ ...

$ du -sh ~/.copilot/installed-plugins/_direct/MLRAgents
170M
$ du -sh ~/.copilot/installed-plugins/_direct/MLRAgents/.venv
169M
$ du -sh ~/MLRAgents/.venv
39M
```

**Did not hold as documented.** The docs state local-path plugins "load live
from the real directory". The install copied the whole tree into
`~/.copilot/installed-plugins/_direct/MLRAgents`, ignored `.gitignore`, and
included the virtualenv — which grew from 39M to 170M because uv's hardlinks
were dereferenced during the copy.

**Consequences.**
1. Development must use `copilot --plugin-dir ~/MLRAgents`, verified in check 6,
   not `copilot plugin install ./`.
2. Nothing may depend on the plugin directory containing a usable virtualenv.
   The hook shim already prefers `mlragents` on `PATH` and falls back to
   `uv run` only for development; the MCP server is launched through `uvx` from
   git for the same reason.
3. Git-based installs (marketplace or GitHub source) clone the repository and
   therefore cannot carry a `.venv`, so this affects development only.

## 6. `--plugin-dir` loads a plugin live, and hooks inherit the environment

Both questions were answered by one run. The shim was temporarily replaced with
a probe that echoes `MLRAGENTS_ROLE`, and the plugin was uninstalled first so
that only `--plugin-dir` could supply it.

```
$ MLRAGENTS_ROLE=explore copilot --plugin-dir ~/MLRAgents \
    -p "Reply with exactly the ROLE_SEEN string you were given at session start, or NO CONTEXT if none." -s
ROLE_SEEN=explore
```

**Both held.**
1. `--plugin-dir` loads the plugin from the working tree with no install step,
   which is the development workflow.
2. **Command hooks inherit the CLI process environment.** Spec §3.3 listed this
   as unverified and specified a `.mlragents/session/<sessionId>.json` fallback
   if it failed. The fallback is not needed and is removed from the spec.

## 7. `--deny-tool` blocks a shell command by name

```
$ copilot -p "Run this shell command and report its output: sbatch --version" \
    --deny-tool='shell(sbatch:*)' --allow-tool='shell' -s
I couldn't run it — the command was blocked by a tool permission rule
(`shell(sbatch:*)`), so no output was produced.
```

**Held.** Confinement of the `explore` agent is enforceable at launch, without a
`preToolUse` hook. This is the load-bearing mechanism of spec §3.3, and it works
as designed: the denial is applied by the CLI, is visible to the model, and the
model cannot talk its way past it.

## Summary

| # | Assumption | Result |
|---|---|---|
| 1 | Hook shim runs standalone, emits JSON, exits 0 | held |
| 2 | Plugin installs and is listed | held; direct installs deprecated |
| 3 | Agent id is the filename | **failed**; plugin agents are `plugin:agent` |
| 4 | `sessionStart` context reaches the model | held |
| 5 | Local-path installs load live | **failed**; full copy, 170M |
| 6 | `--plugin-dir` works; hooks inherit env | both held |
| 7 | `--deny-tool` blocks `sbatch` | held |

Two documented behaviours did not hold. Neither invalidates the design: the
namespacing is a naming correction, and the copy semantics only affect the
development loop, which now uses `--plugin-dir`. The two assumptions the design
actually rested on — environment inheritance and launch-time tool denial — both
held, so role propagation and agent confinement can proceed as specified in
phase 3.
